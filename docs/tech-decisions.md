# GoToTalk: технічні рішення

**Стан на:** 2026-11-15. Рішення ухвалено з Антоном в опитуванні; переглядати лише за його згодою.

## 1. Як ведеться розробка

- Код пише Claude Code; Антон планує, коригує, відповідає на питання. Головне обмеження — ліміти плану Claude Pro.
- Процес: plan mode + офіційний плагін `feature-dev` + spec на сценарій у `docs/specs/` + TDD + Stop-хук «не завершувати з червоними тестами» + reviewer-сабагент на Sonnet. Spec Kit, Superpowers, agent teams і Ralph-цикли не використовуємо.
- Модель: `opusplan` (Opus у plan mode, Sonnet у виконанні). Детально — `docs/WORKFLOW.md`.
- Дозволи: `acceptEdits`, allowlist команд; заборонені `git push`, `drizzle-kit push`, читання `.env`. Агент комітить, push робить Антон.
- Git: приватний репозиторій на GitHub (публічний після захисту); гілка на сценарій, PR, CI (lint, typecheck, тести), `/code-review`.
- Порядок: спершу все на заглушках (Fake-адаптери), потім реальні сервіси, якщо лишиться час.

| 35 | Діалог: текстова відповідь, аналіз, патерни (spec 04a) | **Два кроки:** `POST /api/sessions/:id/utterances` (JSON `{ text }` 1–1000 після trim; лише записує репліку `pending`, моделей не викликає) і `POST /api/sessions/:id/utterances/:utteranceId/analysis` (аналіз і наступне питання). Клієнт викликає крок 2 одразу після кроку 1, тож «аналіз одразу після транскрипції» (рішення 17) виконує клієнт, а не сервер. Відкинуто: один синхронний POST (проміжні стани довелося б імітувати), фонові задачі в процесі з опитуванням (відновлення після рестарту, фонові помилки, нестабільні тести). **Крок 1:** транзакція з `FOR UPDATE` рядка сесії за `id` і `user_id`; сесія `active`, інакше 409 `SESSION_FINISHED`; остання репліка має бути `assistant`, інакше 409 `ANSWER_NOT_EXPECTED` (подвійна відправка); `seq = max + 1`; `text_verbatim = text_clean = text`; облік слів у тій самій транзакції. **Крок 2 ідемпотентний:** стан читається поза блокуванням; аналіз (лише якщо репліка `pending`) і `nextTurn` (лише якщо відповіді `seq + 1` ще немає й сесія `active`) викликаються паралельно (`Promise.allSettled`) поза будь-якою транзакцією, щоб з'єднання пулу не висіло під час виклику моделі; запис іде в транзакції з `FOR UPDATE` рядка сесії й повторною перевіркою стану. Аналіз «захоплюється» `UPDATE … WHERE analysis_status = 'pending'`, помилки й патерни пише лише виклик, що захопив, відповідь `assistant` вставляється `ON CONFLICT (session_id, seq) DO NOTHING` і лише в активній сесії, тож повтор і паралельні виклики дублікатів не дають; ціна: за справжньої гонки модель може бути викликана двічі. Збої: спершу записується те, що вдалося (persist-before-throw), потім кидається помилка; недоступність моделі → 503 `LANGUAGE_MODEL_UNAVAILABLE` (має пріоритет над 502, бо повтор має сенс), репліка лишається `pending`, повтор доробляє решту; дві невалідні відповіді аналізу → `failed` (термінальний, крок завершується 200, `nextTurn` зберігається); дві невалідні відповіді `nextTurn` → 502 `LANGUAGE_MODEL_INVALID_RESPONSE`, повтор можливий. **Відновлення на клієнті:** при завантаженні сторінки клієнт сам викликає крок 2 для останньої репліки `user` активної сесії, якщо в неї немає відповіді або аналіз `pending`; репліка, покинута між кроками, лишається `pending` до наступного відкриття (finish її не доаналізовує, `docs/backlog.md`, spec 05). **Позиції:** `start`/`end` – зсуви в `utterances.text_verbatim` у UTF-16 code units (`end` не включно), `text.slice(start, end) === original` на api й web. Позиції моделі лише підказка: `alignMistakes` лишає помилку, якщо slice збігається, інакше бере найближче до `start` точне входження `original`, без входжень відкидає помилку, потім сортує за `start` і відкидає ті, що перетинаються з попередньою; web захисно пропускає невалідні й перетинні діапазони. Відкинуто: строге відкидання (губить правильні помилки реальної моделі), code points (подвійне перетворення без вигоди для англійського тексту). **Двоярусна валідація відповіді аналізу:** `requestValidated(AnalysisEnvelopeSchema)` перевіряє лише форму (`mistakes` ≤ 30, `better` ≤ 5 елементів `unknown`; невалідний конверт → повтор → `failed`), далі кожна помилка й кожне формулювання проходять `safeParse` окремо, невалідні (чужа категорія, порожній `original`, перевищена довжина) відкидаються, `better` обрізається до 2; у лог лише кількості. Відкинуто: єдина строга схема (одна погана помилка робила б `failed` усю репліку). **Відтворюваність:** `analysis_prompt_version` = id промпту (`error-analysis.v1`, рішення 34), `analysis_model` (Fake: `fake`); обидва повертає порт (`{ output, promptVersion, model }`), сервіс не знає id промпту; значення з останньої відповіді записуються й для `failed`. **Патерни:** +1 до `frequency` за кожну збережену помилку (`INSERT … ON CONFLICT (user_id, category) DO UPDATE`, категорії сортуються перед upsert проти дедлоків) у транзакції запису помилок, `mistakes.pattern_id` заповнюється; «Це не помилка» (`PATCH /api/sessions/:id/mistakes/:mistakeId { isFalse: true }`) ставить `is_false` через `UPDATE … WHERE is_false = false RETURNING category` і лише тоді виконує `frequency = GREATEST(frequency - 1, 0)`, тому повтор не декрементує двічі; скасування позначки не робимо. | Нічого не гарантує одну активну сесію на користувача | 0003: частковий унікальний індекс `sessions_one_active_per_user` (`user_id` WHERE `status = 'active'`); міграція спершу завершує всі активні сесії, крім найновішої |
| Немає де зберігати кращі формулювання з аналізу реплік | 0004: колонка `utterances.better_phrasings` (jsonb NOT NULL, DEFAULT `[]`, CHECK `utterances_better_phrasings_check`: масив); кількість (≤2) обмежує Zod, не CHECK |
| Слова сесії не пов'язані з сесією; звіт не фіксує версію промпту й модель; немає індексу для списку слів | 0005: таблиця `session_words` (PK `(session_id, word_id)`, обидва FK `ON DELETE CASCADE`, індекс `idx_session_words_word`; зв'язки для наявних підказок заповнюються з `hints`); колонки `session_reports.prompt_version` і `model` (nullable); індекс `idx_words_user_created` (`user_id, created_at DESC, id DESC`) для keyset-пагінації слів |

Разом 16 таблиць (0003 і 0004 нових таблиць не додають, 0005 додає `session_words`). Усі міграції перевірено на чистому PostgreSQL.

## 6. Структура коду

Рішення 29. Web (`apps/web/src`): гібрид Bulletproof React і мінімального Feature-Sliced Design. Шари `app → pages → features → shared`, імпорти лише вниз, фіча не імпортує іншу фічу. Api (`apps/api/src`): пласкі доменні модулі NestJS у `modules/`, інфраструктура окремо в `core/`, `common/`, `integrations/`.

| Питання | Рішення і причина |
|---|---|
| Повний FSD (entities, widgets, Steiger) | Не беремо: для двох-трьох доменів і одного розробника зайві шари й інструмент лише множать папки. Беремо від FSD ідею односпрямованих шарів і розділення `pages` та `features` |
| Atomic design | Не беремо: атоми й молекули вже дає Mantine, свій поділ на atoms/molecules/organisms дублював би його й розмивав межі. Компонент однієї фічі лежить у `features/<f>/components/`, спільний для двох і більше фіч – у `shared/ui/` (створюється з першим таким компонентом) |
| Mantine як шар атомів | Власних обгорток над Button/Card не робимо; кастомізація через `theme.components` і `X.extend()` / `X.withProps()`. Тема одна: `app/theme/theme.ts` |
| Barrel-файли `index.ts` | Не використовуємо: вони сповільнюють Vite (dev-сервер і збирання підтягують зайві модулі), легко створюють цикли й ховають реальні залежності. Єдиний `index.ts` – справжній модуль `shared/i18n/index.ts` |
| Аліас `@/` | `@/*` → `apps/web/src/*` у `tsconfig.json`, у Vite 8 підхоплюється через `resolve.tsconfigPaths`. Між папками лише `@/`, відносні імпорти лише в межах однієї папки, ніколи `../../`. В імпортах web немає суфікса `.js` (бандлер резолвить сам; api лишається на ESM NodeNext із `.js`) |
| Контроль меж | `eslint-plugin-import-x` (резолвер `eslint-import-resolver-typescript`): `no-restricted-paths` для шарів і фіч, `no-cycle` для циклів, `no-restricted-syntax` для `../../`. Правила в `error`; тести й `shared/testing` з перевірки меж виключені |
| `shared/api → shared/session` | Залежність односпрямована. `shared/session` – лише клієнтський стан (сховище сесії, кеш запитів), без мережі. `refresh.ts` викликає API та оновлює сесію, тож лежить у `shared/api`; у попередній розкладці `auth/refresh.ts` і `auth/session-store.ts` створювали цикл `http ↔ session-store ↔ refresh` |
| Сторінки | Завжди в папці маршруту `pages/<route>/<Name>Page.tsx`, тонкі (для нового коду). Форми Login/Register/Consent винесемо у `features/auth` при наступній зміні цих сторінок (`docs/backlog.md`) |
| Іменування | Файли й папки компонентів PascalCase, решта kebab-case. Папка на компонент лише коли поруч є `.module.scss` або тест |
| Api: чому лише розділення, а не перебудова | Пласкі модулі «одна папка = одна доменна область» уже збігаються з рекомендованою документацією NestJS структурою, тож їх не чіпаємо. Додано лише розділення інфраструктури (`core`: config, db, logger, errors, health; `common`: спільні декоратори й pipe, як `@Public()`, потрібний і health, тому не в `modules/auth`; `integrations`: порти й Fake-адаптери по можливостях, SDK лише тут) і доменів (`modules`), та розбиття найбільшого модуля `auth` на `guards/`, `decorators/`, `persistence/`, `lib/` (підпапка лише за ≥2 файлів одного типу; корінь модуля тримає module, controller, service(s), errors) |
| Api: без гексагональних шарів `domain`/`mappers` | Не беремо: у модулях мало логіки, яка не залежить від Nest і Drizzle, а мапери й domain-типи подвоїли б кількість файлів без вигоди для одного розробника. Порти потрібні лише на межі із зовнішніми сервісами (STT, LLM) і лежать в `integrations/` |
| Api: без аліасу | В api імпорти відносні з `.js` (ESM NodeNext): аліас потребував би резолвера в рантаймі (tsx, Vitest, збирання) і не дає вигоди при неглибокій вкладеності (максимум `../../../`) |
| Api: контроль меж | Ті самі `eslint-plugin-import-x`: зона `no-restricted-paths` забороняє `core`, `common` і `integrations` імпортувати `modules`; SDK провайдерів дозволені лише в `integrations/**`. Правило в `error`. `apps/api/test/` (інтеграційні тести й `support/`) не реорганізовано |
| `packages/shared` | Розкладати за доменами, коли схем стане ~6+ (`docs/backlog.md`) |

Доповнення до рішення 29: структура v2 (рефакторинг у чотири PR (три з кодом і один із документами); частина рядків вище – v1, де вони суперечать таблиці нижче, чинна v2). Специфікація: `docs/specs/refactor-structure-v2.md`.
